# TASC project: Phase 5 (TASC source recovery)

Started session 5 (2026-10-25). Decisions on integer declarations, line numbering, naming and the page-3 block are in NOTES.md (Decisions).

## [confirmed] MAKE RUNTIME rebuilds RUNTIME byte for byte

RUNTIME is hand-written 6502 (H6), so it has no Applesoft source; Mark decided (2026-10-25) that its build step is an Applesoft program `MAKE RUNTIME` that POKEs the bytes from DATA statements and BSAVEs the file, in line with how the original was probably produced (not described in the manual). Source `src/MAKE_RUNTIME.txt` (165 lines: code at 10-40, DATA 100-1700, 25 bytes per line), `src/MAKE_RUNTIME.DOC.TXT` (line-mirrored, each DATA line's address range), `src/MAKE_RUNTIME.VARS.TXT`; generator and emulator check `python -m tasc.makeruntime`. Line 10 handles the overlap: the bytes go to $0803-$17AF where an Applesoft program normally lives, so if PEEK(104) < 64 it sets TXTTAB to $4001 (POKE 103,1: POKE 104,64: POKE 16384,0) and re-runs itself with PRINT CHR$(4);"RUN MAKE RUNTIME". Line 20 `FOR AD = 2051 TO 6063: READ BY: POKE AD,BY`, line 30 `BSAVE RUNTIME,A$803,L4013` (BSAVE needs the length too, and records the address it saves from, so the bytes must be at $0803). Evidence: experiments/p5_makeruntime/summary.json: on a copy of the TASC 2.01 disk with RUNTIME deleted (HELLO's BLOAD RUNTIME then stops at FILE NOT FOUND, so TASC never runs and DOS is unpatched), RUN MAKE RUNTIME produced RUNTIME, B file at $0803, 4,013 bytes, sha256 3982a702..., identical to the original, in 62M cycles. pytest test_make_runtime_listing checks the DATA bytes and the DOC line mirror without the emulator.

## [confirmed] Phase 5 source generation: names, numbering, documentation (session 5)

`python -m tasc.sourcegen` writes src/PASSn.bas (tokenized), PASSn.txt (listing), PASSn.DOC.TXT, PASSn.VARS.TXT from address-keyed annotations in docs/lift/annot/ (COMMON.ann shared by all passes; PASS1.ann: variable names, groups and meanings, DEF FN names, routine headers, key line comments; `{NAME}` in annotation text becomes the final name). Real TASC compiles the generated PASS0/1/2 sources to files identical to the originals (experiments/p3_selfcompile/*/summary.json: line tables of 305, 1,346 and 501 lines, the sha256 of the originals). Checkers: pytest tests/test_source.py (DOC line numbers mirror the source; every variable in the VARS file with a first-definition comment; names at most two characters, no keyword inside, no collision within a namespace) and test_source_documentation_is_standalone.

Naming constraint (finding): the storage order is determined by the names, so along each pass's allocation order (and routine order) the names' hash buckets h = (3*(c1-1)+c2+T) mod 32 must not decrease, ties in declaration order. With about 100 integers in PASS1 over 32 buckets each variable has a narrow bucket window, so arbitrary meaningful names mostly cannot be kept. The solver (decompile._solve_group) assigns buckets by dynamic programming along the order to maximise name quality: preferred name, then the same first letter with another letter (a fixed first letter reaches 27 of 32 buckets), then the letter alone or with a digit, then the nearest other first letters; a name another variable prefers is penalised. PASS1 result: 13 as preferred, ~89 keep the first letter, ~27 a neighbouring letter. Fallbacks are listed on the development side in docs/lift/annot/PASSn.names.txt (not in the VARS file: standalone rule). Declarations: names in one bucket must be declared in storage order, so groups interleave; INTEGER lines follow group runs, short runs joining the previous line (PASS1: 16 declaration lines).

Numbering (Mark's rules): steps of 10; routine starts (GOSUB targets and ON GOTO/GOSUB targets) at the smallest multiple of 100 that is not the next number; a routine start reached by fall-through skips one number. PASS1 ends at line 21010.

## [confirmed] PASS1 statement-level commentary (session 6)

docs/lift/annot/PASS1.ann now has about 1,000 [lines] entries (from 16): every statement handler, the token reader, line-number and DATA chains, the error reporter, the parser (operands, functions, string expressions, relations, shift-reduce), symbol and temporary management, the emitters and the code generator. Of PASS1's 1,346 lines, 287 have a bare `n REM` (RETURN, plain GOTO, PRINT). Generated PASS1.bas/.txt are unchanged by comments, so the session-5 real-TASC proof still holds for them. Tool: `python -m tasc.annlist PASS1 [first [last]]` prints `$addr  line  text` with every variable as its preferred annotation name in braces ({T}, {SY}(...)) and R/L marks for lines that already carry a routine or line comment; [lines] keys must be line-start addresses from it.

Facts read from the code while commenting (and fixed in the annotations):
- IL ($8FE4, PASS1 FOR) is 1 for a REAL loop variable (`IL = -1 <> K`), not for an integer one. Real loops use limit entry 5 / step 3 / step-1 130; integer loops 125 / 126 / 129. The loop-start call is variable operation 20+IL+ET: 21 int var+int value, 22 real var+int value, 23 int var+real value, 24 both real (PASS2 maps 21-24 to $09E1 $09E5 $09DE $09E8), followed by a 2-byte address placeholder.
- SG ($8FF3) means "the value must be real" (set only by the real-target expression entry, used for LET of a real target and DEF FN bodies; makes 20190/20210 float an integer result with entry 131), not "store through an array element".
- EC (COMMON $17C4, value 2375 = $0947) is a RUNTIME entry that sets S=$FF, rebuilds a base stack frame from $AF/$B0 and falls into RT.RESTORE: it drops every pending GOSUB/FOR and resets the DATA pointer. PASS1 calls it after VAL's ONERR fires (8040) and after reporting a fatal error (7930), since errors can be raised deep inside GOSUBs before compilation continues with the next statement.
- DOS state byte DM ($AA52, DOS 3.3 output-intercept state): PASS1 POKEs 5 (start of a WRITE line: a Ctrl-D starts a command) before each DOS command and 4 (WRITE data: every character goes to the file) before each object byte.
- Token reader pipeline: T current, NT lookahead, IB the byte just read; at T=0 the next two bytes are the link (zero = end of program, NT=-1) and the routine falls through to read the next line number's low byte, so a new line (8220) starts with IB = line number low byte.
- Pending IF..THEN statement JMPs: the JMP's address word is pushed on the operand side of the parse stack and patched at the next line's start (8390) or at the end of the program (6870).
- Call table: CT(i) = PASS0 DATA 2000-2050 (positive = RUNTIME offset, negative = -ROM address); most statement entries are the integer-argument entry, and the call emitter subtracts 3 for a real operand (16500, WT=1); CALL, HIMEM:, SAVE.ADDR and PRINT number hold the real entry (16400, WT=3). For ordinary statements the index is token-128; for operations it is the operation number+64.
- Possible quirk, not tested: the operator-side pop (14100) treats any popped value for which FN OE is true (operators, 0, 40, 41) as an operator, so triple numbers 40 and 41 on that side would look like parentheses.

## [confirmed] PASS0 annotations; listing round-trip fixed (session 6)

docs/lift/annot/PASS0.ann names PASS0's 22 locals (dialog: answer, yes/no result, retry flag, question selector; file specification parsing: name part, slot/drive part, slot/drive given; boot slot and drive from DOS's last-used $AA6A/$AA68; addresses; DATA values), its DEF FNs (SA = address-32767, RA = +32767, SW = signed word) and adds routine headers and line comments (DOS patches, call/operator tables, page-3 code, chain heads, file setup, dialogs). A line typed at a file question that starts with Control-D is executed as a DOS command (e.g. CATALOG) and the question is asked again (PASS0 3460). PASS0 reuses the COMMON variable LS (the listing routine address) as scratch in its file-name trimming before setting it to 909. COMMON DP(I,0) is stored with FN SW (signed word), not as address-32767.

Defects found and fixed: (1) the listing renderer collapsed runs of spaces inside string literals, so PASS0.txt lines 430/440 did not match the program; (2) names ending in A or T join a following keyword when the listing is tokenized again (`VA THEN` -> V, AT, HEN; `KT OR` -> K, TO, R), which the ROM tokenizer also does. names._ok now rejects names ending in A or T, and pytest test_listing_retokenizes checks that cp2 tokenizes each src/PASSn.txt to src/PASSn.bas. Because names are solved jointly over the passes, both changes renamed variables in all three passes; the self-compile proof was re-run afterwards with the final names: real TASC compiles the 305-, 1,344- and 501-line sources into files identical to PASS0, PASS1 and PASS2 (sha256 e500a1ff..., 71768885..., 218d8a5b...), and the full pytest suite passes (22, including the 1,954-compile decompiler round trip).

## [confirmed] PASS2 annotations; all three passes documented (session 6)

docs/lift/annot/PASS2.ann names PASS2's 35 locals (the reference list and its groups, symbol walking, memory layout, file I/O, dispatcher table) and 6 DEF FNs (HB/LO byte split, UB/BI stored-address conversion, TY type without the COMMON +50 mark, LG floor log2), with routine headers and line comments for the whole pass. Read from the code: the reference list holds pairs (latest reference, target) for the DATA chain (target -32767 = 0 at the end), every line symbol (sorted by a shell sort with an odd gap in pairs, then matched against CLINENUM records read in order) and every FN; then per numeric variable/constant a group (latest reference, storage address, entry count+1 negative for an integer, entry address per operation highest first); then (latest reference, routine address) per string variable/array. Constant pool: real constants are always written; integer constants with an empty chain are unlinked (docs/lift/PASS2.md corrected). Constants are then marked 47 (real) / 49 (integer) and COMMON types +50, so TC >= 47 means "address already known, no local storage". Backpatching walks the object in 256-byte file pages from the end; DATA links become 0 for the last block and address-after-the-later-link for each earlier one. The reference list overflow (5900 values) reports TOO LONG. All three passes are in DOCUMENTED; the standalone test allows H1-H7 when it is a variable named in the VARS file (PASS2 has H4). Re-proved: real TASC compiles the 306/1,345/504-line sources into files identical to PASS0/1/2; pytest 24 passed.

## [confirmed] RUNTIME as documented EDASM-style source (session 6)

src/RUNTIME.S (2,725 lines) is the library as 6502 source in the style of Apple's DOS Toolkit assembler (EDASM; Mark chose it as the likely original): labels of at most 8 characters, ORG $0803, EQU for page zero, memory and ROM entry points, DFB for data, `*` comment lines and `;` end-of-line comments. Generated by `python -m tasc.rtsource` from the flow disassembly plus docs/lift/annot/RUNTIME.ann (equates, labels, 66 routine comment blocks, ~450 line comments, data runs). Checked by tasc/edasm.py, a two-pass assembler for exactly that subset with EDASM's rule that a known operand below $100 uses the zero-page form: the source, and its single-spaced disk form, assemble to RUNTIME byte for byte (pytest test_runtime_source_assembles). Written as DFB: the BIT ($2C) opcodes used to skip the next two bytes (28 places) and four absolute,X instructions on page zero (LDA $00F1,X / $00F2,X / $00FF,X, CMP $00FF,X) that reach into the stack page and would be shortened by an assembler. Findings while documenting: the leftover assembler text starts at $109B ("LE? ";:01120:..."; the BCS at $1099 is always taken), not $109E; $0947 RESETSTK (the routine PASS0/1/2 call after errors) leaves FORPOP+8 = $09B8 at the bottom of the stack so a RETURN without GOSUB lands in NORET ($09B9); $1413 ERREXIT is the common error exit, reached through chains of BNE relays with the error number in X; CLEAR CHAIN collects garbage keeping only COMMON strings and then returns into CLEAR (FORPOP-$107 = $08A9); a COMMON mismatch at INIT is error 163 TYPE MISMATCH. HTML: src/html/RUNTIME.html (assembler listing: address, bytes, label, opcode, linked operand, comment, routine blocks as sections) and RUNTIME.OVERVIEW.html (calling conventions, accumulators, inline operands, dispatchers, strings, FOR frame, errors, entries by kind). EDASM cannot assemble one source file that size (Mark), so the disk copy is split (Mark's choice) into src/runtime/RUNTIME.S1-S6: single-spaced, at most 12K each, cut at routine comment blocks, S1 holding the equates and ORG, each part ending with `CHN RUNTIME.Sn+1` so assembling RUNTIME.S1 assembles the library; tasc/edasm.py follows CHN with one symbol table and the chain assembles byte for byte (pytest). src/RUNTIME.S remains the combined reading copy (pushed to RAG as RUNTIME.S.txt). The source disk holds the six parts as DOS text files (20 sectors left), read back from the image and assembled in the check; the RUNTIME overview lists each file's address range.
