# TASC project: Phase 5 (TASC source recovery)

Started session 5 (2026-10-25). Decisions on integer declarations, line numbering, naming and the page-3 block are in NOTES.md (Decisions).

## [confirmed] MAKE RUNTIME rebuilds RUNTIME byte for byte

RUNTIME is hand-written 6502 (H6), so it has no Applesoft source; Mark decided (2026-10-25) that its build step is an Applesoft program `MAKE RUNTIME` that POKEs the bytes from DATA statements and BSAVEs the file, in line with how the original was probably produced (not described in the manual). Source `src/MAKE_RUNTIME.txt` (165 lines: code at 10-40, DATA 100-1700, 25 bytes per line), `src/MAKE_RUNTIME.DOC.TXT` (line-mirrored, each DATA line's address range), `src/MAKE_RUNTIME.VARS.TXT`; generator and emulator check `python -m tasc.makeruntime`. Line 10 handles the overlap: the bytes go to $0803-$17AF where an Applesoft program normally lives, so if PEEK(104) < 64 it sets TXTTAB to $4001 (POKE 103,1: POKE 104,64: POKE 16384,0) and re-runs itself with PRINT CHR$(4);"RUN MAKE RUNTIME". Line 20 `FOR AD = 2051 TO 6063: READ BY: POKE AD,BY`, line 30 `BSAVE RUNTIME,A$803,L4013` (BSAVE needs the length too, and records the address it saves from, so the bytes must be at $0803). Evidence: experiments/p5_makeruntime/summary.json: on a copy of the TASC 2.01 disk with RUNTIME deleted (HELLO's BLOAD RUNTIME then stops at FILE NOT FOUND, so TASC never runs and DOS is unpatched), RUN MAKE RUNTIME produced RUNTIME, B file at $0803, 4,013 bytes, sha256 3982a702..., identical to the original, in 62M cycles. pytest test_make_runtime_listing checks the DATA bytes and the DOC line mirror without the emulator.

## [confirmed] Phase 5 source generation: names, numbering, documentation (session 5)

`python -m tasc.sourcegen` writes src/PASSn.bas (tokenized), PASSn.txt (listing), PASSn.DOC.TXT, PASSn.VARS.TXT from address-keyed annotations in docs/lift/annot/ (COMMON.ann shared by all passes; PASS1.ann: variable names, groups and meanings, DEF FN names, routine headers, key line comments; `{NAME}` in annotation text becomes the final name). Real TASC compiles the generated PASS0/1/2 sources to files identical to the originals (experiments/p3_selfcompile/*/summary.json: line tables of 305, 1,346 and 501 lines, the sha256 of the originals). Checkers: pytest tests/test_source.py (DOC line numbers mirror the source; every variable in the VARS file with a first-definition comment; names at most two characters, no keyword inside, no collision within a namespace) and test_source_documentation_is_standalone.

Naming constraint (finding): the storage order is determined by the names, so along each pass's allocation order (and routine order) the names' hash buckets h = (3*(c1-1)+c2+T) mod 32 must not decrease, ties in declaration order. With about 100 integers in PASS1 over 32 buckets each variable has a narrow bucket window, so arbitrary meaningful names mostly cannot be kept. The solver (decompile._solve_group) assigns buckets by dynamic programming along the order to maximise name quality: preferred name, then the same first letter with another letter (a fixed first letter reaches 27 of 32 buckets), then the letter alone or with a digit, then the nearest other first letters; a name another variable prefers is penalised. PASS1 result: 13 as preferred, ~89 keep the first letter, ~27 a neighbouring letter. Fallbacks are listed on the development side in docs/lift/annot/PASSn.names.txt (not in the VARS file: standalone rule). Declarations: names in one bucket must be declared in storage order, so groups interleave; INTEGER lines follow group runs, short runs joining the previous line (PASS1: 16 declaration lines).

Numbering (Mark's rules): steps of 10; routine starts (GOSUB targets and ON GOTO/GOSUB targets) at the smallest multiple of 100 that is not the next number; a routine start reached by fall-through skips one number. PASS1 ends at line 21010.
